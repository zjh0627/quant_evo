# quant_evo AI原生软件开发生命周期工作流

> 基于 [AI-Native SDLC Playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) 改编

## 概述

**核心理念**: "代码不再是瓶颈，流程才是"

AI使代码生成飞快，但人类节奏的规划、评审、部署仍是瓶颈。本工作流通过六阶段闭环实现快速迭代。

## 第一阶段：PLAN（规划）

### 目标
 originator与Claude直接头脑风暴，用自己的话产出初步需求。

### 产出物
`intent.md` - 存储在 `/Users/keira/keira-data/量化系统/` 目录

### 流程
1. **发起人描述需求** - 用自然语言描述问题和期望
2. **Claude分析** - 识别关键点和约束
3. **生成intent.md** - 包含问题、约束、验收标准
4. **提交到文档目录** - 作为设计阶段的输入

### intent.md模板
```markdown
# Intent: [功能名称]

## 问题/需求
[用自然语言描述]

## 背景
- 当前状态：[描述现状]
- 期望状态：[描述期望]

## 约束条件
- 技术约束：[技术限制]
- 时间约束：[时间要求]
- 数据约束：[数据限制]

## 验收标准
- [可测试的标准1]
- [可测试的标准2]

## 相关方
- 发起人: [姓名]
- 评审人: [姓名]

## 优先级
- P0: [紧急]
- P1: [重要]
- P2: [一般]
```

### 示例
```markdown
# Intent: 行业轮动信号功能

## 问题/需求
当前选股不考虑行业轮动，可能持有弱势行业股票。
需要实现行业动量计算，优先持有强势行业。

## 背景
- 当前状态：按评分排序选股，无行业过滤
- 期望状态：只在动量前5行业中选股

## 约束条件
- 使用申万一级行业（31个）
- 强相关行业互斥（如煤炭/石油/钢铁）

## 验收标准
- [ ] 加载5211只股票的行业数据
- [ ] 正确映射到31个一级行业
- [ ] 强势行业加成+5分
- [ ] 非强势行业评分-10
- [ ] 强相关行业约束生效
```

## 第三阶段：BUILD（构建）

### 目标
 使用Plan Mode生成计划，获得批准后生成代码。

### 产出物
- `plan.md` - 实现计划
- 代码变更（diff）
- 测试用例

### 流程
1. **进入Plan Mode** - Claude分析代码库和spec.md
2. **起草计划** - 生成详细的实现步骤
3. **人类审批** - 审核并批准计划
4. **生成代码** - 按计划实现
5. **生成测试** - 同时生成测试用例

### Plan Mode执行
```
用户: 实现行业轮动功能

Claude (Plan Mode):
1. 读取现有代码结构
2. 分析依赖关系
3. 制定实现计划
4. 展示计划给用户

用户审批后:
Claude:
1. 创建industry_mapping.py
2. 修改evolving_portfolio.py
3. 添加测试
4. 更新文档
```

### 代码规范检查清单
- [ ] 使用类型提示
- [ ] docstring格式正确
- [ ] 遵循命名规范
- [ ] 导入顺序正确
- [ ] 无硬编码值
- [ ] 错误处理完善

## 第五阶段：DEPLOY（部署）

### 目标
 通过PR和评审流程部署代码。

### 产出物
- PR (Pull Request)
- 代码评审记录
- 部署批准

### 流程
1. **创建PR** - Claude创建Pull Request
2. **AI评审** - 自动代码评审
3. **人类评审** - 关键变更人工审核
4. **Hooks检查** - 门禁验证
5. **合并部署** - 满足条件后合并

### PR要求
- 标题：清晰描述变更内容
- 描述：包含动机、变更内容、测试结果
- 关联：关联相关issue/todo

### 评审清单
- [ ] 代码符合CLAUDE.md规范
- [ ] 测试通过
- [ ] IC验证通过
- [ ] 无安全风险
- [ ] 文档已更新

### 门禁检查 (Hooks)
- [ ] lint检查通过
- [ ] 格式化检查通过
- [ ] 测试全部通过
- [ ] 至少1人approve
- [ ] todo.md状态已更新

## 第六阶段：MAINTAIN（维护）

### 目标
 监控运行状态，事故触发新的规划。

### 产出物
- 监控报告
- 事故记录
- 新的intent.md

### 监控指标
| 指标 | 阈值 | 处理 |
|------|------|------|
| 收益率 | < -10% | 告警 |
| 最大回撤 | > 15% | 告警 |
| 信号数量 | = 0 | 检查 |
| 数据延迟 | > 30min | 检查 |

### 事故处理流程
```
检测异常
  ↓
创建事故记录
  ↓
分析根因
  ↓
生成intent.md
  ↓
进入Plan阶段
  ↓
修复问题
  ↓
验证通过后恢复
```

### 事故记录模板
```markdown
# Incident: [时间] [问题简述]

## 概述
[问题描述]

## 时间线
- [时间1] 发现问题
- [时间2] 分析原因
- [时间3] 采取行动
- [时间4] 问题解决

## 根因分析
[根本原因]

## 修复措施
[已采取的修复]

## 预防措施
[防止再次发生的措施]

## 相关方
- 发现人: [姓名]
- 处理人: [姓名]
```

## 关键原则总结

| 原则 | 描述 |
|------|------|
| **Plan Mode** | 先计划后执行，人类审批后再行动 |
| **制品即文档** | 每个阶段产出版本化的制品 |
| **Commit链即审计** | 完整的变更追溯 |
| **Skills指导** | 数据质量、回测验证、风险管理 |
| **Hooks门禁** | 确定性执行检查 |
| **auto-accept是结果** | 不是起点，逐步建立信任 |
| **错误修正入文档** | 同类错误不重复犯 |
| **事故触发规划** | 生产问题转化为新需求 |
